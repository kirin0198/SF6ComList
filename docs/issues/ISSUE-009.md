# ISSUE-009: 疾駆け等の派生技（follow-up moves）をコマンドリストデータモデルに追加

> 作成日: 2026-04-17
> 最終更新: 2026-04-17（カテゴリ横断派生への対応を追記）
> Issue種別: 機能追加
> ステータス: 分析完了・承認待ち
> 関連Issue: ISSUE-001（コマンドリスト入力モード）
> GitHub Issue: https://github.com/kirin0198/SF6ComList/issues/9

## 概要

「特定の技から派生して発生する技（follow-up moves）」をコマンドリストのデータモデルと UI で
表現できるようにする。

派生技は**特定のカテゴリに限定されない**: 必殺技（special）からの派生だけでなく、
ユニーク攻撃（unique）や通常技・コマンド通常技からも派生が存在する。

代表的な派生パターン:

| 派生元カテゴリ | 例                                        | 派生先                                          |
| -------------- | ----------------------------------------- | ----------------------------------------------- |
| `special`      | キンバリー 疾駆け（236+K）               | 急停止・影すくい（中 K）・武神翔霸（中 P）      |
| `special`      | キャミィ フーリガンコンビネーション（214+K） | 各種キック派生                                |
| `special`（構え） | ジェイミー 酔拳、ジュリ 風水エンジン、JP の構え | 構え中の各種技                            |
| `unique`       | ケン 奔雷脚（4+HK）                       | 2段目派生                                      |
| `unique`       | キンバリー 風車（4+HK）                  | 派生キック（2段目）                            |
| `command-normal` / `normal` | ターゲットコンボ系              | 2段目・3段目の派生                              |

このように派生は技カテゴリに依存しない普遍的な概念である。

## 分析結果

### 現状の構造

- `CommandMove` 型には次のフィールドが存在する:
  - `steps: ComboStep[]` — バリアントなし技のステップ
  - `variants?: StrengthVariant[]` — 強度ラベル（L/M/H/OD）ごとの notation + steps
- UI（`CommandListPanel.tsx`）:
  - バリアントあり技はクリックで展開・折りたたみをトグル（`expandedMoveId`）
  - 展開内から弱/中/強/OD のボタンを押すとステップが確定する
- 派生技を表現するフィールドは**存在しない**
- キンバリーの疾駆けは `kimberly-shikkuke` として登録済みだが、派生技（急停止・影すくい・武神翔霸）は未登録

### 派生技が持つ特性

派生技は強度バリアントとは独立した概念であり、両立させる必要がある：

| 特性             | 強度バリアント (variants)     | 派生技 (followUps)                         |
| ---------------- | ------------------------------ | ------------------------------------------ |
| 主な用途         | 弱/中/強/OD のボタン別選択    | 親技の動作中に追加入力で発生する別の技     |
| 親とのつながり   | 同じ技の別ボタン版            | 親技が先行していることが前提               |
| コネクター       | 不要（同一技の選択肢）        | 親技から派生を繋ぐ。`~`（ディレイ/派生）が自然 |
| コンボ上の扱い   | 親技の代わりにどれか1つ       | 親技＋派生技の両方がシーケンスに入る       |
| 派生技自身の強度 | —                              | 派生技自体が L/M/H/OD を持つこともある    |

### 想定ユースケース

ユーザーがキンバリーの「疾駆け（強）から武神翔霸」を登録したい場合:

1. コマンドリストから「疾駆け」を選択 → 強度バリアント「強」を選択 →
   シーケンス: `236HK`
2. 疾駆けのボタン配下に展開された「派生」セクションから「武神翔霸」をクリック →
   シーケンス: `236HK ~ P`（派生コネクターで繋がる）

## 対応方針

### 1. データモデル拡張

`CommandMove` 型に `followUps?: CommandMove[]` を追加する（`src/lib/combo/command-list-types.ts`）。

```typescript
export interface CommandMove {
  id: string;
  name: string;
  nameEn: string;
  category: CommandCategory;
  notation: string;
  steps: ComboStep[];
  /** 強度バリアント（弱/中/強/OD） */
  variants?: StrengthVariant[];
  /** 派生技（親技から発生する follow-up 技） */
  followUps?: CommandMove[];
}
```

#### 設計上のポイント

- **再帰構造**: `followUps` 要素も `CommandMove` とする。派生の派生（ジェイミーのようなケース）や、
  派生技自身が強度バリアントを持つケース（弱/中/強で性能が変わる派生）にも自然に対応できる。
- **カテゴリ非依存**: `followUps` は `CommandMove` のオプショナルフィールドであり、
  親のカテゴリが `special` / `unique` / `command-normal` / `normal` のいずれであっても保持できる。
  つまり**親のカテゴリに関係なく派生を持てる**。
  これにより「疾駆け（special）の派生」と「風車 4+HK（unique）の派生」を
  同じデータ構造・同じ UI 実装で扱える。
- **派生技のカテゴリ**: 親の `category` と独立した値を持てる（親が `special` でも派生側は
  `unique` 相当の動作だったり、その逆もある）。
- **ID 衝突回避**: 派生技の ID は `{characterId}-{parent}-{derivation}` の命名規則で
  キャラクター内ユニークを担保する（例: `kimberly-shikkuke-bushin-shoha`、
  `kimberly-4hk-followup`）。
- **派生コネクター**: 親技 + 派生技 の間に挿入されるコネクターはデフォルトで
  `~`（ディレイ/派生）とする。後述の「データ仕様上のコネクター」で規定する。

#### 代替案と比較

| 案                                                                       | 採用 | 理由                                                                                                    |
| ------------------------------------------------------------------------ | ---- | ------------------------------------------------------------------------------------------------------- |
| A. `followUps?: CommandMove[]`（再帰型）                                | 推奨 | 強度バリアントや派生の派生にも対応可。既存データに破壊的変更なし。型が簡潔。                               |
| B. 派生専用の別型（`FollowUpMove` 等）                                 |      | 再帰・強度バリアントを別扱いにすると二重化する。UI 実装も分岐が増える。                                    |
| C. トップレベルに独立した `CommandMove` として配置し `parentId` で紐付け |      | フラット検索はしやすいが、UI で親のサブに展開する実装が煩雑。シリアライズ時の親子関係がファイル内で見にくい。 |
| D. 派生を別カテゴリ（`followup`）として新設                             |      | カテゴリは技の分類軸であり親子関係を表す軸ではない。責務が混ざる。                                         |

→ **案 A を採用**（既存実装との親和性が最も高い）。

### 2. UI 設計

`CommandListPanel.tsx` を以下のように拡張する。

#### 展開状態の拡張

- 現在の `expandedMoveId: string | null` を維持し、展開状態のトリガーは
  「variants がある」または「followUps がある」または「両方ある」のいずれかに拡張する。
- **展開条件は親のカテゴリに依存しない**: `followUps` を持つ技であれば、
  `special` / `unique` / `command-normal` / `normal` のどのカテゴリでも同じ展開 UI が適用される。
  例: キンバリーの風車（`4HK`, `unique`）を展開すると派生セクションが表示される。
- 展開エリアの構造:

```
[ 親技ボタン（▼） ]
 ├ 強度バリアント行: [ 弱 ] [ 中 ] [ 強 ] [ OD ]
 │   （variants がある場合のみ表示）
 └ 派生技セクション: "派生:" [ 派生技1 ] [ 派生技2 ] ...
     （followUps がある場合のみ表示。親カテゴリは問わない）
```

- 例1（special 配下）: 疾駆け（236+K, special） → [ 急停止 ] [ 影すくい ] [ 武神翔霸 ]
- 例2（unique 配下）: 風車（4+HK, unique） → [ 2段目派生 ]

- 派生技ボタンは親技と同じ `CommandMoveButton` のスタイルを再利用し、
  左端にラベル「派生:」または小さなアイコンを置くことで視覚的に区別する。
- 派生技自身が `variants` を持つ場合、クリック時に従来通り展開される（再帰 UI）。

#### クリック時の挙動（コネクター自動挿入）

- 親技（または親技のバリアント）を選択した直後に派生技を選択した場合、
  派生コネクターとして `~` を自動挿入する。
- 親技以外が最後のステップとなっている場合でも派生技を選べるようにするが、その場合は
  通常の自動挿入ルール（`>`）を適用する。
  - これはシンプルさを優先する方針。派生技を「親技の直後のみクリック可能」にする制約は
    かえって編集体験を損なう可能性があるため、自由度を優先する。
- 「最後が親技か？」の判定は、UI 層ではなく `CommandListPanel` のローカル状態で行う
  （直近に選択された move の id を保持する）。

#### 実装コストの見積もり

- `CommandListPanel.tsx` の変更: 中（展開セクションを2種に分離、再帰レンダリング）
- `command-list-types.ts` の変更: 小（フィールド1つ追加）
- データ JSON の修正: 中（キンバリー疾駆けのみ先行対応、他キャラは段階追加）

### 3. 既存データへの影響 / 先行対応スコープ

- 既存 JSON（全29キャラクター）は `followUps` フィールドがないため**影響なし**（オプショナルフィールド）。

#### キンバリーの派生技一覧（SF6 準拠）

現状の `src/data/command-lists/kimberly.json` を確認した上で、派生を持ちうる技は以下:

| 親技 ID                 | 親技名   | 親カテゴリ | notation | 想定される派生                                                |
| ----------------------- | -------- | ---------- | -------- | ------------------------------------------------------------- |
| `kimberly-shikkuke`     | 疾駆け   | special    | 236+K    | 急停止（K 押下でストップ）／影すくい（K）／武神翔霸（P）      |
| `kimberly-4hk`          | 風車     | unique     | 4+HK     | 派生 2 段目（ターゲットコンボ相当の追撃キック）               |

注: `kimberly-6hk`（飛箭蹴）や `kimberly-3mk`（水切り蹴り）は単発ヒットのユニーク攻撃であり、
固有の派生入力は存在しない（通常のキャンセル対象のため follow-up としては扱わない）。
`kimberly-bushin-senpukyaku`（武神旋風脚）等の他必殺技も同様に派生入力なし。

#### 先行対応スコープの選択肢

| 案   | 対応範囲                                                                 | メリット                                                               | デメリット                                                   |
| ---- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| A 案 | キンバリーの全派生（疾駆け派生 3 種 + 風車 4+HK の 2 段目派生）を一括対応 | カテゴリ横断（special と unique 両方）の実装検証ができる。UI・データの汎用性を初回リリースで担保できる | 追加する派生データが増え、テスト観点も増える                 |
| B 案 | 疾駆け派生 3 種のみ先行。風車派生は別 Issue                              | スコープが小さく実装・レビューが短期化                                 | unique 派生を後追い実装するまで UI 側の検証が片面に留まる    |

**推奨: A 案**。
理由:
1. 本 Issue の眼目が「カテゴリ横断で派生を表現できるデータモデルと UI を作ること」であるため、
   初回から `special` と `unique` の両方で動作検証を行う方が設計の妥当性を担保できる。
2. 追加されるデータは 4〜5 件の派生技に留まり、実装コスト増は軽微。
3. 後追いで `unique` 配下派生を追加する際に UI 側で漏れが発覚するリスクを先に潰せる。

A 案で追加するキンバリー派生技:

- 疾駆け（`kimberly-shikkuke`）配下:
  - `kimberly-shikkuke-stop`（急停止, 疾駆け中 K or P でストップ）
  - `kimberly-shikkuke-kage-sukui`（影すくい, 疾駆け中 K）
  - `kimberly-shikkuke-bushin-shoha`（武神翔霸, 疾駆け中 P）
- 風車（`kimberly-4hk`）配下:
  - `kimberly-4hk-followup`（風車派生 2 段目）

実際の派生入力・派生技名称は SF6 公式コマンド表と JSON データ整備時に最終確認する
（architect → developer フェーズで確定）。

#### 本 Issue のスコープ外

- ジェイミー酔拳配下の派生、ジュリ風水エンジン中技、ディージェイのジャックナイフブースト派生、
  JP 構え派生、キャミィのフーリガン派生、ケンの奔雷脚派生、等の**他キャラ派生は本 Issue 対象外**。
- 別 Issue（ISSUE-010 以降）で段階的に追加する。

### 4. バックエンド（コンボ保存形式）への影響

- 派生技を選択した結果は最終的に `ComboSequence.steps` として通常の `ComboStep` 配列にフラット化される。
- 保存形式である `Combo.sequence` / `Combo.notation` には**一切変更が発生しない**。
- つまり DB マイグレーションは不要。Prisma スキーマにも影響なし。
- `parseNotation` / `serializeNotation` 等の notation 変換ロジックにも変更は不要。

### 5. テストの必要性

- **ユニットテスト（新規/追加）**:
  - `command-list-types.test.ts`: `followUps` を含む JSON の読み込みテスト
- **コンポーネントテスト（CommandListPanel.test.tsx 拡張）**:
  - `special` 配下の派生技セクションが表示されること（例: 疾駆け → 武神翔霸）
  - `unique` 配下の派生技セクションが表示されること（例: 風車 4+HK → 2段目派生）
  - 派生技クリックで `onMoveSelect` が呼ばれ、先頭にコネクター `~` が自動挿入されること
  - `variants` と `followUps` を両方持つ親技の展開挙動
  - 派生技自身が variants を持つ場合の再帰展開
- **E2E / 手動確認**:
  - キンバリーのコマンドリストで疾駆けを選択 → 派生武神翔霸 で
    `236HK ~ HP` のようなシーケンスが構築されること
  - キンバリーの風車（4+HK, unique）を選択 → 派生2段目 で
    `4HK ~ ...` のようなシーケンスが構築されること
